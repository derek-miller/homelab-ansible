# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Ansible-managed homelab. k3s (server rackvm1, agents rackvm2-5, amd64 VMs on the pve1-5 Proxmox cluster) runs the user-facing services from `kubernetes/` via Flux; Docker stays on the rackvms to build images and on the Pis for Compose; a Mac mini (`rackmini1`) runs Plex, Homebridge, OpenClaw, Tailscale and the SMB mounts. One playbook, `playbooks/default.yml`, organised as sequential plays selected by tag.

## Read this before editing anything

- **Service config lives in Ansible Vault, not in the tree you can grep.** The Pis' Compose stacks are `docker_compose_definition` in each Pi's `vars.yml`, with their secrets vaulted inline, and rackmini1 keeps its secrets in `host_vars/rackmini1/vault.yml`. A plain grep reads vaulted text as opaque AES blobs and reports it absent — decrypt (`make vault-decrypt`) before concluding anything is undeclared.
- **Kubernetes apps live in `kubernetes/`, applied by Flux, not Ansible.** A `*.vault.yaml` file there is vault-encrypted whole. Hidden apps must not be named by any file name, plain file, comment or deploy output; the repo and its Actions logs are public. Every namespace in `kubernetes/` carries the default-deny baseline copied from `kubernetes/portainer/namespace.yaml` (RUNBOOK.md, Apps on k3s).
- **Run `make vault-encrypt` before committing.** `hooks/pre-commit` runs `make vault-check` and rejects the commit otherwise. The Makefile hard-errors unless `VIRTUAL_ENV` is set, so commit from inside `.venv`.

## Commands

```bash
make after-git-pull     # Install all deps after pulling
make run                # Default playbook, all hosts
make run hosts=rackvm1  # Limit to a host
make run tags=docker    # Limit to a tag (implies --skip-tags=base,common)
make run tags=flux      # Deploy only the k3s apps in kubernetes/
make dry-run            # --check
make lint               # yamllint (CI requires lint and test)
make test               # Role test suites
make check              # lint + test + syntax check
make bootstrap hosts=<host> user=<user>

# make {run,dry-run,check,bootstrap}-<name> runs playbooks/<name>.yml, paired with
# playbooks/hosts-<name> as inventory when that file exists. hosts=/tags= work here too.
make bootstrap-proxmox user=root   # First contact: asks for the PAM password, authorises
                                   # the repo key for root, then forms or joins the cluster
make run-proxmox hosts=pve3 tags=proxmox-cluster

# Vault
make vault-diff         # Vault changes (use for commit messages)
make vault-encrypt      # Required before commit
make vault-decrypt      # Decrypt for editing
make vault-check        # Verify encryption (pre-commit hook)

# Dependencies
make -B requirements.txt              # Recompile Python deps
make -B requirements.txt UPGRADE=1    # Upgrade unpinned packages
make -B init install UPGRADE=1        # Upgrade every lock, the roles' too, and sync the venv
make galaxy-install                   # Reinstall Galaxy roles/collections
```

## Conventions

- Inventory groups in `playbooks/hosts` are by **function** (`docker`, `k3s_server`, `raspberry-pi`, `smb-shares`, ...), not by machine, and carry inline vars. Plays in `default.yml` select on them by tag.
- `playbooks/roles/galaxy/` is gitignored and generated by `make galaxy-install` from `roles/requirements.yml`, so it is absent from a fresh clone. The checked-in roles are `ansible/` (connection/bootstrap), `common/`, and `generic/`.

- **Placement is by node label, never by hostname.** Each label is declared on exactly one host as a comma-delimited `node_labels` in the `[node_labels]` inventory group, and the flux role puts each label on its node as `homelab.local/<label>: "true"` and as the ServiceLB pool `<label>`: a suite's pods pin with that node selector and its LoadBalancers with `svccontroller.k3s.cattle.io/lbpool: <label>`. Volumes come from the `local-retain` storage class.
- **A role that installs something splits `present.yml` / `absent.yml`,** routed from `tasks/main.yml` on a `<role>_state` variable. `absent` must fully reverse `present`: stop the service, remove config, uninstall the package, clear the repo and keyring.
- Secrets in group_vars and host_vars are inline `!vault` values, except in a host's whole-file `vault.yml`, whose `vault_<name>` values its `vars.yml` reads indirectly. Layering is role defaults → group_vars → host_vars.
- **A secret that could get root on a host, read or delete backups, change DNS or certificates, sign in as someone else, push code or images, or drive the bot goes in an `infra` file;** if unsure, it does. That is `infra.yml` beside the `vars.yml` (inline, never a `vault.yml`), the namespace's `kubernetes/<ns>/infra.vault.yaml`, or `playbooks/files/vault/infra/`. A key moved to `infra.yml` must leave `vars.yml`, which loads after it and would win.
- Ingress annotations (`router.entrypoints`, `router.middlewares`) carry routing and sign-in on k3s.
- Images the `generic/docker/build-images` role makes are tagged by a hash of their inputs (files, base image digest or source commit) and pushed to the cluster's image registry as that tag and `<name>:latest`, where apps on k3s name it `registry.homelab.local/<name>`. Nothing gets a version bump; a changed input rebuilds, and the same deploy pins the apps that name it to the new digest.
